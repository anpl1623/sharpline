# ADR 0009: The frontend's data plane — generated types, client-side odds formatting, REST for the tree and WebSocket for movement

- **Status:** Accepted
- **Date:** 2026-08-19
- **Charter reference:** CLAUDE.md §6, §7, §11 (phase 7), §12

## Context

Phase 7 builds the frontend against two contracts that already exist and are already
enforced: `internal/httpapi/openapi.yaml`, from which the Go server types and `pkg/client`
are generated and drift-checked by `make codegen-check`; and `internal/wsgw`'s
snapshot-then-delta protocol, documented at length in `internal/wsgw/doc.go`.

Both contracts describe the *same entities*. A market has one id in Postgres, in the
compacted `price.computed` topic, in the REST response and in a WebSocket delta. That
overlap is the whole reason the board can be server-rendered from REST and then updated in
place from the stream — and it is also the reason the frontend has four decisions to make
that will otherwise be made accidentally, differently, in four different components.

**The two feeds carry the same prices in different shapes.** REST returns
`Market.selections[].prices[]` — a selection with one `Price` per quoting book, plus a
server-computed `best_price`. The stream carries `pricing.ComputedMarket` — a market with
one `BookAssessment` per book, each holding one quote per selection, alongside the devigged
fair value and the per-quote EV. They join on `(market_id, selection_id, book_slug)`. What
is *not* symmetric is the display metadata: the REST `Price` object can carry a rendered
`display` string when `odds_format` is `american` or `fractional`; the stream carries only
`decimal`, because `price.computed` is a pricing record and has no opinion about
presentation.

**Odds formats are lossy in one direction only.** Phase 1 settled that Decimal is canonical
and that American and Fractional are display formats: `odds.RenderAmerican` and
`odds.RenderFractional` round, and the round trip back is not the identity. The OpenAPI spec
restates it — `decimal_odds` travels unconditionally on every price object, and
`odds_format` only *adds* a `display` string beside it.

**The delta rail is a hard rendering constraint, not a flourish.** `DESIGN.md` specifies a
2px rail per price cell with a hard onset, a 180ms digit roll and a 2500ms decay, and then
constrains the implementation: "`transform` and `opacity` only. Never animate layout.
Per-cell decay timers; do not re-render the row." A league snapshot observed on the running
stack was 123 markets, each with two to three selections quoted by five books. Any design
where one price change re-renders a row — let alone a table — does not survive that.

**There is no charting dependency in the tree and adding one is not free.** The production
image budget is 200MB (CLAUDE.md §7) and `web/next.config.ts` already spends several
paragraphs of reasoning on `outputFileTracingExcludes` to hold it.

Left undecided, every one of these resolves the wrong way by default: hand-written fetch
types that silently stop matching the spec, a `display` string on the board that vanishes
the moment the stream takes over, a REST poll running beside the socket and double-rendering
every change, and a charting library whose default palette is green-and-red.

## Decision

### D1 — the TypeScript types are generated from `openapi.yaml`, committed, and drift-checked

`web/src/lib/api/schema.ts` is produced by `openapi-typescript` from
`internal/httpapi/openapi.yaml` — the same file the Go server types and `pkg/client` come
from. It is generated by `make codegen-ts`, committed, and `make codegen-check-ts` (wired
into `make codegen-check`, which CI's `generated` job runs) regenerates into a throwaway
path and fails on any diff.

The generator runs in the existing `npm` tools container from the committed lockfile, so it
adds no host dependency. `deploy/compose/compose.tools.yaml` mounts the spec **read-only at
the fixed path `/openapi.yaml`** rather than letting the container reach it relatively:
`/app` is `web/`, and nothing above it is mounted, so `../internal/...` does not resolve.
The spec is an input, not a sibling file the frontend can reach around.

`pkg/client` is deliberately *not* the frontend's client. It is a Go SDK; the browser needs
TypeScript. Both are generated from the same YAML, which is the property that matters.

### D2 — odds format conversion happens client-side, from `decimal_odds`

The frontend always requests decimal (the default) and never reads the `display` field. The
conversion lives in `web/src/lib/odds/format.ts`, ported function-for-function from
`internal/domain/odds` with the correspondence named in comments.

The reason is D3, below: the WebSocket carries only `decimal`. If the board rendered REST
prices from `display` and streamed prices from a client-side conversion, the two would be
free to disagree — and the disagreement would appear as a price that changes format the
first time it moves, which reads as a rendering bug and is nearly impossible to attribute.
One conversion, one code path, both feeds.

`implied_probability` (REST) and `implied` (stream) are `1/decimal` **with the book's vig
still in them**. They are never labelled as fair probabilities anywhere in the UI; the
devigged number is `fair.selections[].probability` on the stream payload and is shown in the
mono engineering register beside the method that produced it.

### D3 — REST is the source for the tree; the WebSocket is the source for movement. No polling.

A board page is a React Server Component that fetches `/board` (or
`/leagues/{slug}/board`) with `cache: 'no-store'` over the in-network service name, so the
first paint is real prices with no client waterfall and no spinner. It hands that page to a
client component which subscribes to the league channels present in it and applies deltas in
place by `(market_id, selection_id, book_slug)`.

The catalogue structure — which events exist, which markets hang off them, which selections
under those — comes from REST and only from REST. Price *movement* comes from the socket and
only from the socket. TanStack Query is configured with no `refetchInterval` anywhere on
board or event data: a poll running beside the socket would render the same change twice,
once with a delta rail and once without, and the second render would look like a spurious
flash.

A delta naming a market that is not on the current page is dropped, not merged — it belongs
to another keyset page.

### D4 — the delta rail is driven imperatively on the DOM node, not through React state

Each price cell subscribes at *cell* granularity via `useSyncExternalStore` against the live
slate, and restarts the rail animation on its own DOM node. No parent re-renders, and no
2500ms decay timer ever becomes a React state tick. `prefers-reduced-motion` shortens the
rail to a 400ms linear fade and makes the digit swap instant — it does **not** remove the
rail, because the rail carries information.

Direction is computed from the previous decimal held in the slate. A byte-identical decimal
is *not* a change and fires nothing: most polls upstream are no-ops, and lighting the board
for them is exactly the "noise, not information" failure CLAUDE.md §7 names.

### D5 — the line-movement chart is hand-rolled SVG

No charting library. The chart reads `/selections/{id}/history`, whose points are OHLC by
design ("the mean of a line is a price nobody traded at"), and draws close as a line with a
faint high–low band, in `ink-2` with `delta-in`/`delta-out` for direction. A `422` — the
window and resolution would exceed `max_points` — is surfaced with the resolution the API
says *would* fit, never silently truncated.

## Consequences

**Made easy.** A field renamed in `openapi.yaml` breaks the frontend build in CI rather than
at runtime, in the same commit that renames it. The board renders identically whether a
price arrived over REST or over the socket, in any of the three odds formats. A dense board
updates without re-rendering a row, so the recency gradient the decay rail exists to produce
actually forms. The chart inherits the design system exactly, including the deliberate
absence of green and red.

**Made hard.** The odds conversion is now implemented twice in this repository — once in Go,
once in TypeScript — and the two must agree. That is a real duplication and the honest
mitigation is that the TypeScript port names its Go counterpart function-for-function, so a
change on one side has an obvious address on the other. Generating the TypeScript from the
Go would be better and is not possible without a third representation.

**Cost accepted.** `make codegen-check` is now slower: `codegen-check-ts` runs `npm ci`
before it can generate, because CI starts from a bare runner with an empty `node_modules`
volume. Roughly a minute, paid on every run, to close the same drift hole the sqlc and
oapi-codegen halves already close. Committing generated code and then checking it is the
pattern this repo already uses twice; a third instance is consistency, not novelty.

**Also accepted.** The `display` field remains in the OpenAPI contract, is served by the
API, and is used by nothing in this frontend. Removing it would be a spec change that breaks
`pkg/client` consumers for the benefit of one client's internal preference, which is not a
trade worth making. Its presence is not dead weight for a Go SDK consumer that wants the
server to do the rendering.

## Alternatives considered

**Hand-write the fetch types.** Rejected: the spec is ~78KB and describes 18 paths with
`additionalProperties: false` on almost every schema. Hand-written types would be wrong
within a week and wrong *silently*, which is the exact failure the spec-first pipeline was
built to prevent for the Go side. The repo already pays the committed-generated-code cost
twice; refusing to pay it a third time for the client that a human actually looks at would
be backwards.

**Use `pkg/client` via a Go-to-WASM bridge, or generate TypeScript from the Go types.**
Rejected: both introduce a third representation of the contract sitting between the YAML and
the browser, and the YAML is already the single source. WASM additionally lands megabytes in
a 200MB image budget for the benefit of removing one generator.

**Render odds from the API's `display` field.** Rejected on D2's grounds: the stream cannot
supply it, so the board would need a second rendering path for streamed prices, and the two
paths would drift. A secondary reason is latency — the format toggle would become a network
round trip and a full board refetch, when it is a pure function of a number already on the
client.

**Poll REST alongside the socket as a safety net.** Rejected: it double-renders every
change, and it hides exactly the failure it is meant to protect against. A stream that has
silently stopped delivering is a defect that must be *visible*; the status rail reports it in
words and the sequence-gap resync recovers from it. A poll quietly papering over a dead
socket means nobody ever finds out the socket was dead — which is the same argument
`internal/wsgw` D3 makes for stamping the sequence number at enqueue so a dropped buffer
shows up as a gap the client can see.

**Recharts / visx / Chart.js.** Rejected: each ships a default palette and a default set of
affordances built around green-up/red-down, which is the precise convention `DESIGN.md`
departs from and argues at length about departing from. Overriding a chart library into this
design system costs more code than drawing an OHLC line in SVG, and adds a dependency to a
bundle that is under an explicit size budget. The series being drawn is one line and one
band; that is not a library-shaped problem.

**Card-per-event on mobile instead of a horizontally scrolling table.** Rejected in
`DESIGN.md`'s newly-resolved mobile section rather than here, but it belongs on this list
because it is the decision most likely to be re-argued: it destroys the column scan a board
exists for, breaks the "every price is a table cell with an accessible name" contract, and
triples scroll length. The accepted cost of the alternative — horizontal scrolling is a worse
gesture — is named there.
